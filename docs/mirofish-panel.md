## 1. What was run

[MiroFish](https://github.com/666ghj/MiroFish) — a multi-agent swarm
simulation engine on CAMEL-AI's OASIS — cloned and run **for real**, on
6 October 2026, against the seven personas from
[feedback-hypotheses.md](feedback-hypotheses.md).

That document previously said the tool had *not* been run, for two reasons:
it needed a paid LLM key plus a Zep Cloud key, and it simulates thousands of
agents while this project's entire AI budget is UnoRouter's free tier. Both
objections were **overridden by the founder**, and the objections turned out
to be half-right:

| Claimed blocker | What actually happened |
|---|---|
| Needs a Zep Cloud key | **True for the Flask app, false for the engine.** Zep is wired into `app/api/graph.py`, `simulation.py` and the report agent — but **not** into `backend/scripts/run_*.py`. The panel ran with no Zep account at all. |
| Simulates thousands of agents, blowing the quota | **Wrong unit of analysis.** MiroFish's cost is *agents × rounds*. The engine also exposes an `INTERVIEW` manual action, which lets a panel be interviewed without any social rounds. Cost was **one request per persona**. |
| Needs Python 3.11–3.12 | True (`requires-python = ">=3.11,<3.13"`; this machine had 3.13.7). Solved with `uv python install 3.12`. |
| Needs a paid LLM key | **False for this shape of run.** The existing UnoRouter free-tier key was sufficient for 7 requests. |

The engine ran unmodified. No file in the MiroFish clone was patched.

**Total cost: 7 LLM requests.** Paced at 70s apart (UnoRouter free tier is
~1 req/min account-wide). Zero 429s.

## 2. What it was asked

The seven personas from `feedback-hypotheses.md` were interviewed with the
**exact instrument** the live `/feedback` page shows — the five faces from
`RATING_SCALE`, the six `BEST_TAGS`, the nine `IMPROVE_TAGS`, the five
`SPECIES_OPTIONS`, verbatim from
[`server/src/lib/feedback.ts`](../server/src/lib/feedback.ts). Same wording,
so the answers are at least *about* the thing real farmers will be asked.

Each persona was then asked three open questions: what would have to be true
to use Wangari daily, what would you change first, and who else would want
this.

## 4. Verdicts on our own hypotheses

| # | Claim | Verdict |
|---|---|---|
| **H1** | Most-chosen "best" is *works offline*, not the AI advice | **Refuted.** Offline drew 3/7 and ranked third. *Easy* and *records correct* tied at 5. |
| **H2** | Most-chosen "improve" is a *missing feature*, not speed or bugs | **Refuted as written.** *Needs internet* (6) outranked *missing feature* (5). But the substance survives: speed and difficulty drew 1 each. |
| **H3** | ≥⅓ choose *"I need training"* or *"language confusing"* | **Supported (weakly).** *Training* 3/7 = 43%. Both were named by non-farmers (co-op chair, county officer, investor) — i.e. the activation gap, not a software gap. |
| **H4** | Public no-login link beats the in-app prompt | **Not testable here.** It compares two real acquisition channels. A simulation cannot observe response rates. Real traffic is the only evidence. |

**The contradiction worth keeping.** The personas chose *works offline* as a
delight (3/7) while simultaneously naming *it needs internet* as their single
biggest complaint (6/7). Read one way, that is noise: the prompt offered the
offline tag, so personas reached for it. Read another way it is the sharpest
signal in the run — **connectivity is the thing they want more of, not the
thing they are delighted by.** Under R8 (offline-first) that is a problem
worth naming out loud rather than claiming offline as a headline feature.

## 5. The finding that matters

**Sarah Mutua — the investor — filled out the farmer form and rated it 1/5.**

She is not a farmer and never will be. She rated an app she would never open,
chose *kuku, mifugo, mazao, samaki, nyuki* as her species, and listed nine
improvements. Her single most useful sentence: *"I would have to be a farmer
actively managing my farm."*

The public link at `wangari.imeantech.com/feedback` has **no audience filter**.
Anyone with the URL can submit — a prospective investor, a curious investor, a
journalist counting users. Under the never-inflate rule, that is exactly the
wrong person to poll, because the one number an investor takes away from an
open link is *how many people answered*.

This is a real defect in the thing we shipped on 6 October, found by a
simulation, and it is cheap to fix: gate the public form behind one extra tap
("I am a farmer / agritech adviser / other") and segment the admin summary by
it. Until then, the response count on that link means less than it appears to.

## 6. Why this is still not evidence

Stated plainly, because this document exists to be honest rather than
flattering:

1. **It is circular.** The same model family wrote the personas *and* answers
   them. The panel cannot surprise the person who wrote it. It confirms that a
   persona can be made to sound like a persona — nothing more.
2. **It cannot be falsified by being believed.** Only the `Feedback` table,
   filled in by real people, settles H1–H3.
3. **Multi-tap invites satisficing.** Personas chose 2–4 tags from a list.
   Real farmers will tap fewer. Treat the tallies as *ordering*, not as
   *prevalence*.
4. **Seven is not a sample.** It is a smoke test of the instrument's wording.

What it *did* buy, honestly: two hypotheses killed before a farmer wasted a
minute on them, one contradiction surfaced, and one live defect in the public
link identified. That is a good afternoon's work for 7 requests.

## 7. Reproducing it

```bash
git clone --depth 1 https://github.com/666ghj/MiroFish.git
cd MiroFish/backend && uv python install 3.12 && uv sync

# .env at the MiroFish repo root — the SAME UnoRouter key the server uses
printf 'LLM_API_KEY=<key>\nLLM_BASE_URL=https://api.unorouter.com/v1\n' > ../.env
printf 'LLM_MODEL_NAME=qwen3-next-80b-a3b-instruct:free\n' >> ../.env

cp -r <wangari>/tools/wangari-panel ../wangari-panel
uv run python ../wangari-panel/run_panel.py
```

`SMOKE_LIMIT=1` rehearses a single persona first. Results append to
`panel_results.json` after each interview, so an interrupted run resumes
instead of paying for the panel twice. The runner paces itself at 70s and
serialises the OASIS semaphore at 1 — raise `PACE_SECONDS` if you point it at
a paid key, and expect cost to scale with *rounds*, not personas.
